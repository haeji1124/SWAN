## 프롬프트 1 — 사이트 구조와 흐름 전체 설계

너는 정보 구조(IA)와 사용자 흐름을 설계하는 UX 설계자야. 아래 기획 내용을 바탕으로 **SWAN 웹사이트의 사이트 구조와 사용자 흐름**을 설계해 줘. 시각 디자인(색, 글꼴)은 다루지 말고 구조와 흐름에만 집중해 줘.

### 1. 서비스 배경
- SWAN(SW Academy for Newbie)은 사내 SW 교육이다. 한 기수 약 10명, 8주 과정, 1년에 2~3회 모집하며 4기까지 진행했다.
- 이 사이트는 교육과 운영 파트를 홍보하고, 교육 신청을 받고, 졸업생의 완성작을 보여주는 사내망 웹사이트다.
- 사내망 PC에서만 접속한다. 모바일 화면은 설계하지 않는다.
- 랜딩은 스크롤에 따라 아기 오리가 자라 백조가 되는 3D 연출이 깔린다(newbie의 8주 성장). 3D는 랜딩에 집중하고 나머지 화면은 읽기 쉬운 2D다.

### 2. 풀어야 할 문제
- 지금은 모집을 메일로 공지하고 메일로 신청받는다. 메일만으로는 뭘 배우는지, 내 수준에 맞는지 전달되지 않는다.
- 듣고 싶은 사람이 8주 파견 부담과 "교육 후 어떤 기대를 받게 될지" 걱정 때문에 신청을 망설인다.
- 궁극적 페인포인트: "듣고 싶은 마음은 있는데, 교육이 끝난 뒤의 내 모습을 미리 볼 방법이 없다."
- 그래서 이 사이트의 설득 수단은 **졸업생의 실제 완성작**이다. 설명보다 증거를 먼저 보여준다.

### 3. 사용자 유형과 권한
| 유형 | 어떤 사람 | 할 수 있는 것 |
|---|---|---|
| 방문자 (비로그인) | 예비 수강생, 부서장, 실장님 등 사내 직원 누구나 | 모든 공개 화면 보기 |
| 로그인한 직원 | SSO로 로그인한 사내 직원 | 교육 신청, 다음 기수 알림 받기 |
| 졸업생 | 관리자가 졸업 처리했거나 명단에 등록한 직원 | 본인 완성작 등록·수정 |
| 관리자 | 운영 파트 담당자 | 기수, 신청, 졸업생, 갤러리 검수, 관심 등록자 관리 |

대표 인물
- 예비 수강생: 공정 엔지니어 5년차. 코딩 경험이 거의 없고, 모집 메일의 링크를 눌러 들어온다. 신청을 고민하는 순간이 가장 중요한 순간이다.
- 보는 사람: 부서장(파견 결재), 실장님·사업부장님(성과 보고를 받음). 로그인 없이 랜딩과 갤러리만 훑어본다.

### 4. 핵심 행동
- 가장 중요한 행동은 **교육 신청** 하나다: ① 완성작·커리큘럼을 본다 → ② 내 수준에 맞는지 확인한다 → ③ 신청서를 제출한다.
- 주 행동 버튼은 "신청하기" 하나로 통일한다. 첫 화면의 버튼은 작게, 정보를 다 본 뒤 페이지 끝의 버튼을 크게 둔다.

### 5. 화면 목록 (이번 범위)
| 화면 | 역할 | 들어가는 내용 |
|---|---|---|
| 랜딩 | 첫인상과 전체 소개 | 인트로 연출 → 히어로(한 줄 소개, 작은 신청 버튼) → 교육 소개 → 완성작 미리보기 → 커리큘럼 요약 → 파트 소개 → FAQ → 큰 신청 버튼 |
| 커리큘럼 | 8주 과정 상세와 수준 판단 | 8주 타임라인(수면 위 징검돌 8개) → 주차별 내용 → 수강 대상·사전 지식 → 신청 버튼 |
| 갤러리 목록 | 졸업생 완성작 쇼케이스 | 기수 필터 → 완성작 카드 → (졸업생에게만) 등록 버튼 |
| 완성작 상세 | "교육 후의 내 모습" | 대표 이미지 → 제목·만든 사람·기수·부서 → 무슨 문제를 풀었나 → 어떻게 풀었나 → 스크린샷 → 효과 수치 |
| 완성작 등록·수정 | 졸업생이 완성작을 올림 | 제목, 문제 설명, 해결 방법, 효과, 대표 이미지, 스크린샷 |
| 신청 | 핵심 행동 | 활성 기수 정보 → 폼(사번, 부서명, 이름, 녹스 아이디) → 접수 완료 연출과 이후 일정 안내 |
| 관리자 | 운영 | 탭 5개: 기수 / 신청 목록 / 졸업생 / 갤러리 검수 / 관심 등록자 |
| 로그인 | SSO 연결 | 로그인 후 원래 하려던 화면으로 돌아감 |

### 6. 반드시 반영할 규칙
- **기수**: 관리자가 "활성 기수"를 하나 지정한다. 신청은 사용자가 기수를 고르지 않고 활성 기수로 자동 접수된다. 한 사람은 한 기수에 한 번만 신청할 수 있다.
- **모집 기간이 아닐 때**: 활성 기수가 없으면 사이트의 모든 "신청하기"가 "다음 기수 알림 받기"로 바뀐다. 누르면 로그인 후 관심 등록이 된다. 알림은 자동 발송이 아니라, 관리자가 관심 등록자 명단을 보고 모집 메일을 보낸다.
- **로그인 시점**: 보는 것은 전부 로그인 없이 가능하다. 신청, 알림 받기, 완성작 등록, 관리자 화면에서만 로그인을 요구한다.
- **완성작 검수**: 등록하면 "검수 대기"가 되고 관리자가 승인해야 공개된다. 반려 시 사유가 작성자에게 보인다. 승인된 완성작을 수정하면 다시 검수 대기가 된다. 검수 대기·반려 상태는 작성자와 관리자만 볼 수 있다.
- **졸업생 인식**: 사이트로 신청해 수료한 사람은 관리자가 신청 목록에서 "수료 처리"하면 졸업생이 된다. 기존 1~4기 졸업생은 관리자가 수동으로 등록하며, 아직 로그인한 적 없는 사람도 사번으로 미리 등록할 수 있다.
- **범위 밖** (설계하지 말 것): 토이프로젝트 팀원 모집, 알림 센터, 성과 요약, 파견/비파견 선택, 메신저·메일 자동 발송, 신청 취소·내 신청 내역, 모바일 화면. 다만 나중에 "토이프로젝트" 메뉴가 추가될 자리가 내비게이션에 있는지는 표시해 줘.

### 7. 만들어 줄 결과물
아래 순서대로, 각 항목에 제목을 붙여서 만들어 줘.

**A. 사이트맵**
- 전체 화면의 계층 구조를 나무 형태로 그리고, 각 화면의 주소(경로)를 제안해 줘.
- 화면마다 접근 권한(누구나 / 로그인 / 졸업생 / 관리자)을 표시해 줘.
- mermaid 도표로도 그려 줘.

**B. 내비게이션 설계**
- 상단 메뉴 항목과 순서, 각 사용자 유형(방문자, 로그인한 직원, 졸업생, 관리자)에게 메뉴가 어떻게 다르게 보이는지 표로 정리해 줘.
- "신청하기" 버튼이 상태에 따라 어떻게 바뀌는지 정리해 줘: 활성 기수 있음·미신청 / 이미 신청함 / 활성 기수 없음·관심 미등록 / 관심 등록 완료.
- 랜딩 안에서의 이동(섹션 바로가기)과 화면 사이 이동을 구분해 줘.

**C. 화면별 구조**
- 화면마다 위에서 아래로 놓이는 블록, 각 블록의 목적 한 줄, 그 블록에서 갈 수 있는 다음 화면을 표로 정리해 줘.
- 랜딩은 섹션별로 "이 섹션이 예비 수강생의 어떤 걱정에 답하는지"와 "이 구간에서 오리가 어떤 성장 단계인지"를 함께 적어 줘.
- 화면마다 빈 상태, 로딩, 오류 상태에서 무엇을 보여줄지 적어 줘. (예: 승인된 완성작 0건, 활성 기수 없음)

**D. 사용자 흐름도** (각각 mermaid flowchart)
1. 예비 수강생: 메일 링크 → 랜딩 → 탐색 → 신청 완료. 비로그인 상태에서 신청을 누른 경우와 이미 신청한 경우의 갈림길 포함
2. 모집 기간이 아닐 때: 다음 기수 알림 받기
3. 졸업생: 로그인 → 완성작 등록 → 검수 대기 → 승인 또는 반려 → 수정 후 재검수
4. 관리자: 새 기수 생성·활성화 → 신청 목록 확인 → 교육 종료 후 수료 처리 → 기수 비활성화
5. 관리자: 갤러리 검수 (승인 / 반려와 사유)
6. 관리자: 기존 졸업생 수동 등록
7. 보는 사람(부서장·실장님): 링크 → 랜딩 → 갤러리 → 완성작 상세

각 흐름에는 시작 계기, 결정 지점(마름모), 끝났을 때 사용자가 보는 화면을 넣어 줘.

**E. 상태 전이도**
- 완성작: 검수 대기 / 승인 / 반려 사이의 전이와 누가 일으키는지
- 신청: 접수 / 수료
- 기수: 준비 / 활성(모집 중) / 종료
- mermaid stateDiagram으로 그려 줘.

**F. 권한 표**
- 행은 기능(화면 보기, 신청, 관심 등록, 완성작 등록, 본인 완성작 수정, 검수, 기수 관리 등), 열은 사용자 유형 4가지인 표를 만들어 줘.
- 권한이 없는 사람이 주소로 직접 들어왔을 때 어디로 보내는지도 적어 줘.

**G. 빠진 곳과 질문**
- 위 규칙만으로 결정할 수 없었던 부분, 흐름이 막히는 지점, 서로 충돌하는 규칙을 목록으로 정리해 줘.
- 항목마다 네가 권하는 선택과 이유를 한 줄씩 적어 줘. 임의로 정해서 설계에 넣은 부분은 "가정"이라고 표시해 줘.

### 8. 설계 원칙
- 예비 수강생이 랜딩에서 신청 완료까지 가는 길이 가장 짧고 분명해야 한다. 다른 흐름이 이 길을 방해하면 안 된다.
- 증거(완성작)가 설명(커리큘럼)보다 먼저 온다.
- 기획에 없는 기능이나 화면을 새로 추가하지 않는다. 필요하다고 판단되면 G 항목에 제안으로만 적는다.
- 화면에 들어갈 문구는 한국어로 쓴다.

## 프롬프트 2 — 랜딩 스크롤 설계 구체화
랜딩 화면만 더 자세히 설계해 줘. 스크롤 진행률 0~100%를 구간으로 나누고, 구간마다 ① 화면에 보이는 글 섹션 ② 오리의 성장 단계와 카메라 위치 ③ 이 구간에서 누를 수 있는 것 ④ 예비 수강생이 이 구간에서 얻는 확신을 표로 정리해 줘. 인트로 로딩 연출이 끝나는 시점, 드래그할 수 있는 소품이 놓이는 위치, 신청 버튼이 커지는 지점도 표시해 줘. 3D를 쓸 수 없는 PC에서 같은 내용이 정지 이미지로 어떻게 보이는지도 함께 적어 줘.

## 프롬프트 3 — 예외 흐름 점검
지금 설계에서 사용자가 길을 잃거나 막힐 수 있는 경우를 찾아 줘. 최소한 다음을 다뤄 줘: 신청 폼 작성 중 로그인이 풀림 / 신청 직후 관리자가 기수를 비활성화함 / 졸업생이 아닌 사람이 완성작 등록 주소로 직접 들어옴 / 반려된 완성작을 고치지 않고 방치함 / 수동 등록한 졸업생의 사번이 틀림 / 승인된 완성작이 0건인 채로 사이트를 엶. 경우마다 사용자에게 보여줄 화면과 문구, 돌아갈 곳을 정해 줘.

## 프롬프트 4 — 관리자 화면 구조 구체화
관리자 화면의 탭 5개를 각각 설계해 줘. 탭마다 목록에 보일 열, 정렬·필터, 한 줄에서 할 수 있는 동작, 여러 줄을 골라 한 번에 할 수 있는 동작, 되돌릴 수 없는 동작의 확인 절차를 정리해 줘. 관리자가 한 기수를 처음부터 끝까지 운영할 때 탭을 오가는 순서도 흐름도로 그려 줘.

## 프롬프트 5 — 2단계 확장 자리 확인
나중에 토이프로젝트 팀원 모집(모집 글 작성, 참가 신청, 작성자 승인), 사이트 내 알림, 성과 요약이 추가된다. 지금 구조에서 이 기능들이 들어갈 자리(메뉴, 주소, 화면)를 표시하고, 지금 설계를 바꾸지 않고 추가할 수 있는지 확인해 줘. 바꿔야 하는 부분이 있으면 지금 미리 고쳐 둘 것과 나중에 고쳐도 되는 것으로 나눠 줘.
