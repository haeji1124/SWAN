# SWAN 웹사이트 — Claude Code 작업 프롬프트

사용법: 빈 폴더에서 Claude Code를 열고, 같은 폴더의 `CLAUDE.md`를 프로젝트 루트에 복사한 뒤 아래 Phase를 순서대로 하나씩 붙여넣는다. 한 Phase가 끝나면 "확인"을 직접 해 본 다음 다음 Phase로 간다.

순서의 이유: 동작하는 2D 사이트를 먼저 완성하고(Phase 0~3), 그 위에 3D 연출을 올린다(Phase 4~5). 3D가 늦어져도 쓸 수 있는 사이트가 남는다.

---

## Phase 0. 프로젝트 셋업

CLAUDE.md를 읽고 프로젝트 뼈대를 만들어 줘.

- 폴더 구조: `frontend/` (React + Vite + TypeScript + Tailwind), `backend/` (FastAPI + SQLite)
- 개발 중에는 Vite 개발 서버가 `/api` 요청을 FastAPI로 넘기도록 프록시를 설정
- 디자인 토큰을 Tailwind 테마로 정의: 물빛 파랑(주색), 흰색(바탕), 오리 노랑(강조), 둥근 모서리, 본문 글꼴. 글꼴 파일은 저장소에 포함하고 `@font-face`로 불러온다 (외부 링크 금지)
- 공통 레이아웃: 상단 고정 메뉴 — 소개 / 커리큘럼 / 갤러리 / 신청하기 버튼, 오른쪽에 로그인 상태
- 라우트(빈 페이지): `/` 랜딩, `/curriculum` 커리큘럼, `/gallery` 갤러리 목록, `/gallery/:id` 완성작 상세, `/gallery/new`와 `/gallery/:id/edit` 완성작 등록·수정, `/apply` 신청, `/admin` 관리자
- 서버: CLAUDE.md의 데이터 모델 5개(User, Cohort, Application, Interest, Project) 테이블 생성
- 임시 로그인: 인증을 한 모듈로 분리하고 지금은 임시 구현만 만든다. 로그인 버튼을 누르면 테스트 사용자 목록(비졸업 직원 2명, 졸업생 2명, 관리자 1명)에서 고르는 화면이 나오고, 고르면 세션이 생긴다. 나중에 SSO 구현으로 바꿔 끼울 자리를 주석으로 표시
- 샘플 데이터 넣는 스크립트: 가상의 사용자 5명, 기수 4개(1~4기, 모두 종료) + 5기(활성, 모집 중), 승인된 완성작 6건(가상의 자동화 과제, 대체 이미지 포함), 검수 대기 완성작 1건

수용 기준
- [ ] 명령 하나씩으로 서버와 화면 개발 서버가 뜬다 (README에 실행 방법)
- [ ] 모든 경로가 열리고 상단 메뉴가 보인다
- [ ] 임시 로그인으로 사용자를 바꿀 수 있고, 새로고침해도 로그인이 유지된다
- [ ] 샘플 데이터 스크립트를 다시 실행해도 중복 없이 초기 상태가 된다

확인: 개발 서버 실행 → 메뉴로 모든 페이지 이동 → 임시 로그인으로 관리자와 졸업생을 번갈아 선택.

다 되면 만든 것과 실행 방법을 요약해 줘.

## Phase 1. 핵심 루프: 교육 신청

이 사이트의 중심인 "보고 → 확신하고 → 신청한다" 흐름을 2D로 먼저 만들어 줘. 3D는 Phase 4에서 올리니 지금은 히어로 자리에 정지 이미지나 단색 배경을 둔다.

사용자 상황: 공정 엔지니어 5년차가 사무실 PC에서 모집 메일의 링크를 누르고 들어온다. 듣고는 싶지만 내 수준에 맞는지, 뭘 얻는지 몰라 망설이고 있다.

화면: 랜딩 `/`
- 레이아웃(위→아래): 히어로(한 줄 소개 + 작은 신청 버튼) → 교육 소개 → 완성작 미리보기(승인된 완성작 3건 카드) → 커리큘럼 요약(8주를 한 줄씩) → 파트 소개 → FAQ(접었다 펴기) → 큰 신청 버튼
- FAQ에는 "코딩을 처음 해도 되나요", "8주 동안 현업은 어떻게 하나요", "교육 후에는 무엇을 하게 되나요"를 포함 (문구는 임시로 작성하고 TODO 표시)
- 완성작 카드를 누르면 `/gallery/:id`로 이동 (상세 화면은 Phase 2)

화면: 신청 `/apply`
- 활성 기수가 있을 때: 기수 정보(이름, 교육 기간) → 폼(사번, 부서명, 이름, 녹스 아이디 — 로그인 정보로 미리 채움, 수정 가능) → 제출
- 제출 후: 접수 완료 화면 + 이후 일정 안내 (연출은 Phase 5)
- 활성 기수가 없을 때: 신청 버튼 대신 "다음 기수 알림 받기" → 확인 팝업 → 관심 등록
- 비로그인 상태에서 신청이나 알림 받기를 누르면 로그인 후 원래 하려던 화면으로 돌아온다

수용 기준
- [ ] 신청하면 현재 활성 기수로 접수된다 (사용자가 기수를 고르지 않는다)
- [ ] 같은 기수에 두 번 신청할 수 없고, 이미 신청했으면 "신청 완료" 상태가 보인다
- [ ] 활성 기수가 없으면 사이트의 모든 신청 버튼이 "다음 기수 알림 받기"로 바뀐다
- [ ] 관심 등록은 한 사람당 한 번만 저장된다
- [ ] 필수 항목이 비면 제출되지 않고 어느 칸인지 알려준다
- [ ] 서버 API에 대한 자동 테스트: 정상 신청, 중복 신청 거부, 활성 기수 없음, 비로그인 거부

확인: 비로그인으로 랜딩을 끝까지 스크롤 → 신청 → 임시 로그인 → 폼 제출 → 완료 화면. DB에서 활성 기수를 끄고 다시 들어가 "다음 기수 알림 받기"가 되는지 확인.

다 되면 만든 것과 확인 방법을 요약해 줘.

## Phase 2. 커리큘럼과 갤러리

화면: 커리큘럼 `/curriculum`
- 레이아웃: 8주 타임라인(주차 번호 + 제목) → 주차를 누르면 그 주 내용이 펼쳐짐 → 수강 대상·사전 지식 안내 → 신청 버튼
- 주차별 내용은 프런트의 데이터 파일 하나로 관리하고 임시 문구를 넣는다 (나중에 실제 내용으로 교체)

화면: 갤러리 목록 `/gallery`
- 레이아웃: 제목 → 기수 필터 → 완성작 카드 그리드(대표 이미지, 제목, 기수, 부서, 효과 한 줄) → 졸업생에게만 "완성작 등록" 버튼
- 승인된 완성작만 보인다. 졸업생 본인에게는 자기 완성작이 검수 상태 표시와 함께 보인다

화면: 완성작 상세 `/gallery/:id`
- 레이아웃: 대표 이미지 → 제목·만든 사람·기수·부서 → 무슨 문제를 풀었나 → 어떻게 풀었나 → 스크린샷 → 효과(수치를 크게)
- 본인 완성작이면 수정 버튼

화면: 완성작 등록·수정 `/gallery/new`, `/gallery/:id/edit`
- 폼: 제목, 문제 설명, 해결 방법, 효과, 대표 이미지 1장, 스크린샷 여러 장
- 등록하면 "검수 대기" 상태가 되고, 승인된 완성작을 수정하면 다시 "검수 대기"가 된다
- 반려된 경우 반려 사유가 보인다

수용 기준
- [ ] 졸업생이 아닌 사용자는 등록 버튼이 보이지 않고, 주소로 직접 들어가도 등록할 수 없다 (서버에서도 막는다)
- [ ] 검수 대기·반려 상태의 완성작은 작성자와 관리자 외에는 목록과 상세 모두에서 보이지 않는다
- [ ] 이미지는 종류와 크기를 검사하고 서버 폴더에 저장한다
- [ ] 기수 필터가 동작하고, 결과가 없을 때 안내 문구가 나온다
- [ ] 랜딩의 완성작 미리보기 카드가 상세로 이어진다
- [ ] 권한 검사에 대한 자동 테스트

확인: 졸업생으로 로그인해 완성작 등록 → 목록에 "검수 대기"로 보임 → 다른 사용자로 바꿔 보이지 않는지 확인.

다 되면 요약해 줘.

## Phase 3. 관리자 화면

화면: 관리자 `/admin` (관리자만 접근)
- 탭 1 기수: 기수 목록, 새 기수 만들기, 활성화/비활성화. 하나를 활성화하면 기존 활성 기수는 자동으로 꺼진다
- 탭 2 신청 목록: 기수별 신청자(사번, 이름, 부서명, 녹스 아이디, 신청 시각). 선택한 신청자를 "수료 처리"하면 그 사용자가 해당 기수 졸업생이 된다. 목록을 CSV로 내려받기
- 탭 3 졸업생: 졸업생 목록, 수동 등록(사번, 이름, 부서명, 녹스 아이디, 기수) — 기존 1~4기 등록용. 아직 로그인한 적 없는 사람도 사번으로 미리 등록하면 첫 로그인 때 졸업생으로 인식된다
- 탭 4 갤러리 검수: 검수 대기 목록 → 내용 미리보기 → 승인 또는 반려(사유 입력)
- 탭 5 관심 등록자: 목록과 CSV 내려받기 (새 기수 모집 메일 발송용)

수용 기준
- [ ] 관리자가 아니면 화면과 API 모두 접근할 수 없다
- [ ] 활성 기수는 항상 최대 1개다
- [ ] 수료 처리된 사용자가 다시 로그인하면 갤러리 등록 버튼이 보인다
- [ ] 승인하면 완성작이 즉시 공개되고, 반려하면 작성자에게 사유가 보인다
- [ ] 관리자 지정은 환경 설정(관리자 사번 목록)으로 한다
- [ ] 관리자 API에 대한 자동 테스트

확인: 관리자로 6기를 만들고 활성화 → 직원으로 신청 → 관리자로 신청 목록 확인 후 수료 처리 → 그 직원으로 완성작 등록 → 관리자로 승인 → 비로그인으로 갤러리에서 확인.

여기까지가 3D 없이 완전히 동작하는 사이트다. 다 되면 전체 흐름을 요약해 줘.

## Phase 4. 3D 랜딩: 오리에서 백조로

랜딩에 사이트의 대표 장면을 올려 줘. 컨셉은 "아기 오리가 스크롤을 따라 자라 백조가 된다"로, newbie의 8주 성장을 뜻한다. 참고 구조는 Leeroy의 Atmos처럼 화면에 고정된 3D 캔버스 위로 글 섹션이 스크롤되는 방식이다.

- 기술: react-three-fiber + drei, 스크롤 연동은 GSAP ScrollTrigger(scrub)
- 장면: 잔잔한 수면, 밝은 하늘, 수면 위의 로우폴리 아기 오리
- 모델: 지금은 기본 도형을 조합한 임시 오리와 임시 백조를 코드로 만든다. 나중에 Blender에서 만든 `.glb` 파일로 바꿀 수 있게 모델 컴포넌트를 분리하고, 교체 방법을 README에 적는다
- 히어로: 마우스를 움직이면 오리의 고개가 따라오고 수면에 물결이 인다
- 스크롤: 카메라가 수면 위 경로를 따라 이동한다. 섹션(교육 소개 → 완성작 → 커리큘럼 → 파트 소개)을 지날 때마다 오리가 조금씩 자라고, 마지막 신청 버튼 앞에서 백조가 되어 날개를 편다. 장면 변화는 하나의 타임라인으로 관리한다
- 인트로: 첫 접속 때 짧은 로딩 연출(진행률 표시 후 화면이 열림). 2초를 넘기지 않고, 같은 세션에서 다시 들어오면 생략
- 글 섹션은 3D 위에 읽기 쉽게 올린다 (반투명 패널 등). Phase 1에서 만든 내용과 버튼은 그대로 동작해야 한다

성능과 대체
- 품질 단계 3개: 전체 / 축소(픽셀 비율 제한, 물결·그림자 끔) / 정지 이미지. 실행 중 프레임 속도를 재서 느리면 단계를 내린다
- WebGL을 못 쓰는 브라우저와 움직임 줄이기 설정에서는 정지 이미지로 보여준다
- 화면에 보이지 않을 때는 렌더링을 멈춘다
- 외부로 나가는 요청이 없어야 한다. three.js 보조 파일(Draco 등)을 쓰면 저장소에 넣고 로컬 경로로 지정한다. 모델이 작으면 압축을 쓰지 않는다

수용 기준
- [ ] 스크롤을 올리고 내릴 때 장면이 스크롤 위치와 정확히 맞물린다 (빠르게 스크롤해도 어긋나지 않는다)
- [ ] 개발자 도구의 네트워크 탭에 외부 도메인 요청이 0건이다
- [ ] 개발 모드에서 품질 단계를 강제로 바꿔 볼 수 있다 (주소의 쿼리 등)
- [ ] 정지 이미지 단계에서도 모든 내용과 신청 버튼이 정상 동작한다
- [ ] 랜딩을 떠났다 돌아와도 메모리가 계속 늘지 않는다 (형상·재질 정리)

확인: 랜딩을 처음부터 끝까지 천천히, 그리고 빠르게 스크롤. 품질 단계를 강제로 바꿔 보기. 브라우저의 성능 탭에서 프레임 속도 확인.

다 되면 장면 구성과 모델 교체 방법을 요약해 줘.

## Phase 5. 나머지 연출

랜딩 밖의 화면에 가벼운 연출을 더해 줘. 정보 화면은 읽기가 우선이니 과하지 않게 한다.

- 커리큘럼: 8주 타임라인을 수면 위 징검돌 8개로 표현. 돌을 누르면 그 주차 내용이 펼쳐진다. 가벼운 3D 또는 CSS 3D 중 더 단순한 쪽으로
- 갤러리: 카드에 마우스를 올리면 입체로 살짝 기울어진다 (CSS)
- 신청 완료: 깃털이 흩날리는 짧은 연출 (2~3초)
- 드래그 요소: 랜딩 히어로에 끌어 움직일 수 있는 장난스러운 소품 2~3개(예: 스티커, 수면 위 소품)와 원위치 버튼. 소이정 사이트의 드래그 스티커에서 착안
- 스크롤에 따라 섹션이 등장하는 연출을 커리큘럼·갤러리에도 통일해서 적용

수용 기준
- [ ] 움직임 줄이기 설정에서는 모든 연출이 꺼지거나 최소화된다

## Phase 6. 다듬기와 반입 준비

- 빈 상태, 로딩, 오류 상태를 모든 화면에 넣는다 (완성작 0건, 서버 오류, 이미지 누락 등)
- 폼 오류 문구, 버튼 문구, FAQ 문구를 일관되게 다듬는다
- 접근성: 버튼 이름, 색 대비, 초점 표시
- 넓은 모니터(1920px)와 작은 노트북(1366px) 폭에서 레이아웃 점검
- 운영용 빌드: 화면을 빌드해 FastAPI가 정적 파일과 `/api`를 함께 서비스하도록 구성하고, 명령 하나로 실행되게 한다
- 오프라인 점검: 네트워크를 끊은 상태에서 운영용 빌드를 띄워 모든 화면이 정상인지 확인하고, 외부 주소 문자열이 소스와 빌드 결과에 남아 있지 않은지 검색한다
- 반입 문서 `docs/반입-가이드.md` 작성
  - 가져갈 것 목록: 소스, npm 패키지, 파이썬 패키지(오프라인 설치용 묶음 만드는 방법 포함)
  - 사내에서 할 일: SSO 연동 지점과 구현해야 할 함수, 관리자 사번 설정, DB 교체 방법, 임시 로그인 끄기, 샘플 데이터 지우고 실제 데이터 넣기, 오리·백조 모델 교체
  - `.wasm` 등 정적 파일의 형식 설정과 보안 정책에서 확인할 점
- 임시 로그인은 환경 설정으로만 켜지게 하고, 운영 설정에서는 기본으로 꺼 둔다

수용 기준
- [ ] 네트워크를 끊고도 운영용 빌드의 모든 화면이 동작한다
- [ ] 자동 테스트가 모두 통과한다
- [ ] 반입 가이드만 보고 새 PC에서 설치와 실행이 가능하다

확인: 인터넷을 끊고 운영용 빌드 실행 → Phase 3의 전체 시나리오를 다시 수행.

## 부록: 기획 근거 요약
- 문제: 모집 메일만으로는 교육에서 뭘 얻는지, 내 수준에 맞는지 알 수 없고, 8주 파견 부담과 교육 후 기대가 걱정돼 듣고 싶은 사람이 신청을 망설인다
- 궁극적 페인포인트: "듣고 싶은 마음은 있는데, 교육이 끝난 뒤의 내 모습을 미리 볼 방법이 없다."
- 목표 지표: 갤러리 완성작 수, 사이트를 통한 신청, 부장님이 성과 보고에 사이트를 사용, 다른 파트의 제작 문의
- 기획자의 개인 목표: 이 사이트로 웹 개발 역량을 보여준다. 그래서 랜딩의 완성도와 매끄러운 동작이 기능 수보다 중요하다
